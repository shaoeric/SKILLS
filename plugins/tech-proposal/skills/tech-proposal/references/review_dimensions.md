# 6 维度审查打分细则

## 评分标准

| 分数 | 含义 |
|------|------|
| 1 | 严重缺失 — 该维度几乎没有覆盖 |
| 2 | 不足 — 覆盖了部分但存在重大遗漏 |
| 3 | 及格 — 基本覆盖，无重大遗漏 |
| 4 | 良好 — 覆盖全面，细节到位 |
| 5 | 优秀 — 超出预期，有深入思考 |

## 维度详解

### 1. 需求覆盖度（Requirements Coverage）

检查 proposal 是否满足 `requirements.md` 中的所有必做项。

| 检查点 | 说明 |
|--------|------|
| 必做项覆盖 | 所有 Q1a 核心功能是否都有对应模块？ |
| 不做项未越界 | 是否引入了 Q1c 明确排除的功能？ |
| 成功指标对齐 | 架构设计是否服务于 Q1b 成功指标？ |
| 技术限制遵守 | 是否避开了 Q1d 中禁止的技术栈？ |

### 2. 技术可行性（Technical Feasibility）

检查方案在技术上是否可行。

| 检查点 | 说明 |
|--------|------|
| 选型与调研一致 | 每个技术选型能否追溯到 research.md？ |
| 组件兼容性 | 所选技术栈是否存在已知的兼容性问题？ |
| 社区成熟度 | 所选开源组件是否有足够的社区活跃度？ |
| 无不可行设计 | 是否存在已知不可行的架构设计？ |

### 3. 性能可量化（Performance Quantifiability）

检查方案是否能量化满足 Q2 的性能要求。

| 检查点 | 说明 |
|--------|------|
| 并发能力 | 架构能否满足 Q2a 的并发要求？ |
| 延迟指标 | 关键路径设计能否达到 Q2b 的延迟要求？ |
| 吞吐设计 | 是否有明确的吞吐量设计方案？ |
| 可伸缩性 | 是否说明了水平/垂直扩展策略？ |

### 4. 方案完整性（Solution Completeness）

检查方案是否无遗漏。

| 检查点 | 说明 |
|--------|------|
| 模块无遗漏 | 是否覆盖了从输入到输出的完整链路？ |
| 输入输出定义 | 每个模块是否明确定义了输入/输出？ |
| Corner Cases | 每个模块是否覆盖了 4+ 种 corner case？ |
| 流程图完整 | 每个模块是否有流程图？架构是否有整体图？ |

### 5. 排期合理性（Timeline Reasonableness）

检查人力和排期估算是否靠谱。

| 检查点 | 说明 |
|--------|------|
| 人力估算合理 | 每个模块的人力需求是否在合理范围？ |
| 依赖关系正确 | 前后驱模块的依赖关系是否正确？ |
| 关键路径识别 | 是否识别了关键路径（最长依赖链）？ |
| 缓冲时间 | 是否预留了适当的缓冲时间？ |

### 6. 风险覆盖（Risk Coverage）

检查风险识别是否充分。

| 检查点 | 说明 |
|--------|------|
| 技术风险 | 是否识别了关键技术风险？ |
| 人员风险 | 是否考虑了关键人依赖？ |
| 进度风险 | 是否有进度延误的应对措施？ |
| 缓解措施有效 | 每个风险的缓解措施是否具体可行？ |

## 通过标准

- 所有 6 维度得分 ≥ 3 分
- 无 BLOCKER 级别问题
- → 审查结论: PASS
