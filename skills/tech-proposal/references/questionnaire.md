# 结构化需求问卷 — 选择式交互

## 核心原则

⚠️ **IRON RULE**: 禁止向用户提问答题。必须将每个维度转化为选择题（单选/多选），由 Agent 根据用户场景推断可能的选项，用户只需勾选，Agent 负责总结。

## 交互流程

```
用户描述场景（1-2句话）
    ↓
Agent 分析场景 → 推断可能的特征
    ↓
Agent 使用 AskUserQuestion 逐轮提问（每轮 ≤4 题，每题 2-4 选项）
    ↓
用户勾选选择
    ↓
Agent 将选择结果转化为 requirements.md
    ↓
用户确认 requirements.md → 锁定
```

## 提问策略

### 原则

1. **场景驱动推断**: 先理解用户场景，再生成针对性的选项。不同场景的选项完全不同。
2. **降低用户负担**: 每题给 2-4 个选项，让用户点选而非打字。
3. **提供"不确定"出口**: 每题都包含"不确定/后续再定"选项，不强迫用户回答不确认的问题。
4. **Agent 负责总结**: 用户选完后，Agent 将选项翻译为结构化的需求边界描述。

### 提问轮次设计

| 轮次 | 覆盖维度 | 题目数 | 说明 |
|------|---------|--------|------|
| 第 1 轮 | Q1 范围边界 | 3-4 题 | 先问清楚要做什么、不做什么 |
| 第 2 轮 | Q2 性能规模 + Q5 任务模式 | 3-4 题 | 性能和任务模型通常关联 |
| 第 3 轮 | Q3 数据情况 | 3-4 题 | 数据源、量级、质量 |
| 第 4 轮 | Q4 使用方式 | 3-4 题 | 产品形态、部署、平台 |
| 第 5 轮 | Q6 约束条件 | 2-4 题 | 时间、人力、预算 |

> Agent 可根据实际情况合并/跳过轮次。如用户需求简单，2-3 轮即可。

## 各维度出题指南

### Q1: 范围边界

**Agent 推断逻辑**: 根据用户场景描述，列出该场景常见的功能模块，让用户选择哪些做、哪些不做。

**示例** — 用户说"我想做一个智能客服系统"：

```
题目: 以下功能哪些是本期必须做的？（多选）
选项:
  - [ ] A. 文本对话（文字问答）
  - [ ] B. 语音对话（语音识别+合成）
  - [ ] C. 人工客服转接
  - [ ] D. 知识库管理后台
  - [ ] E. 数据分析看板
  - [ ] F. 多渠道接入（微信/网页/API）

题目: 以下哪些功能明确不做或后续再考虑？（多选）
选项: [同上列表，但用于标记"不做"]
```

**转为 requirements.md**:
```markdown
## 1. 范围边界
- 核心功能: 文本对话、知识库管理后台
- 后续考虑: 语音对话、数据分析看板
- 明确不做: 人工客服转接、多渠道接入
```

### Q2: 性能与规模

**Agent 推断逻辑**: 根据场景类型推断量级选项（小/中/大），给出具体数字区间。

**示例**:
```
题目: 预期的用户规模是？
选项:
  - [ ] A. 小规模（日活 < 100，并发 < 10）
  - [ ] B. 中等规模（日活 100-1000，并发 10-50）
  - [ ] C. 大规模（日活 1000-10000，并发 50-200）
  - [ ] D. 超大规模（日活 > 10000，并发 > 200）

题目: 对响应速度的要求是？
选项:
  - [ ] A. 实时（P99 < 500ms，如在线对话）
  - [ ] B. 准实时（P99 < 3s，如搜索结果）
  - [ ] C. 普通（P99 < 30s，如报表生成）
  - [ ] D. 无严格要求
```

**转为 requirements.md**:
```markdown
## 2. 性能与规模
- 并发: 日常 10-50 / 峰值 < 100
- 延迟: P99 < 500ms（实时对话场景）
```

### Q3: 数据情况

**Agent 推断逻辑**: 根据场景推断数据来源类型，给出常见选项。

**示例**:
```
题目: 数据主要从哪里来？（多选）
选项:
  - [ ] A. 用户上传文件（PDF/Word/图片等）
  - [ ] B. 数据库已有数据
  - [ ] C. 第三方 API 接入
  - [ ] D. 实时流数据

题目: 数据量级大概多少？
选项:
  - [ ] A. 小（< 1GB，几百条）
  - [ ] B. 中（1-100GB，万级）
  - [ ] C. 大（100GB-1TB，百万级）
  - [ ] D. 超大（> 1TB，千万级以上）

题目: 数据质量如何？
选项:
  - [ ] A. 已清洗干净、结构化
  - [ ] B. 有噪音但可用
  - [ ] C. 大量缺失、需要预处理
  - [ ] D. 不确定，需要评估

题目: 是否有数据合规要求？
选项:
  - [ ] A. 无特殊要求
  - [ ] B. 企业内部数据，需私有部署
  - [ ] C. 个人隐私数据（需符合 GDPR/等保）
  - [ ] D. 金融/医疗等强监管行业
```

### Q4: 使用方式

**示例**:
```
题目: 产品最终以什么形态交付？
选项:
  - [ ] A. Web 网页应用（浏览器访问）
  - [ ] B. API 服务（供其他系统调用）
  - [ ] C. 桌面客户端
  - [ ] D. 移动端 App

题目: [如选桌面客户端] 目标操作系统？
选项:
  - [ ] A. 仅 Windows
  - [ ] B. 仅 macOS
  - [ ] C. 跨平台（Win + Mac + Linux）
  - [ ] D. 不确定

题目: 部署方式偏好？
选项:
  - [ ] A. 公有云（阿里云/腾讯云/AWS 等）
  - [ ] B. 私有化部署（自家机房）
  - [ ] C. 混合云
  - [ ] D. 单机/离线运行

题目: 技术栈是否有开源免费要求？
选项:
  - [ ] A. 必须全部开源免费
  - [ ] B. 尽量开源，可接受少量商业组件
  - [ ] C. 商业组件无限制
  - [ ] D. 不确定
```

### Q5: 任务模式

**示例**:
```
题目: 用户请求的方式主要是？
选项:
  - [ ] A. 同步（提交后立即返回结果，如 ChatGPT 对话）
  - [ ] B. 异步轮询（提交任务→返回 task_id→轮询结果）
  - [ ] C. 异步回调（提交任务→完成后主动通知）
  - [ ] D. 流式返回（结果逐字/逐条推送，如 SSE）

题目: 单次任务处理的时长通常是？
选项:
  - [ ] A. 秒级（< 5s，如文本翻译）
  - [ ] B. 分钟级（1-10min，如文档解析）
  - [ ] C. 小时级（> 1h，如批量数据分析）
  - [ ] D. 混合（短任务为主，偶有长任务）

题目: 是否已确定技术组件？（多选）
选项:
  - [ ] A. 消息队列（Kafka / RabbitMQ / Redis）
  - [ ] B. 数据库（PostgreSQL / MySQL / MongoDB）
  - [ ] C. LLM 模型（OpenAI / Claude / 开源）
  - [ ] D. 向量数据库（Milvus / Pinecone / pgvector）
  - [ ] E. 以上均未确定
```

### Q6: 约束条件

**示例**:
```
题目: 交付时间要求？
选项:
  - [ ] A. 紧急（1-2 周内 MVP）
  - [ ] B. 正常（1-2 个月）
  - [ ] C. 充裕（3-6 个月）
  - [ ] D. 暂无明确截止日期

题目: 团队人员配置？
选项:
  - [ ] A. 单人（全栈独立开发）
  - [ ] B. 小团队（2-5 人，有前后端分工）
  - [ ] C. 中大团队（5-15 人，角色齐全）
  - [ ] D. 暂无团队，需要外包/招聘

题目: 是否有预算限制？
选项:
  - [ ] A. 零预算（仅使用免费服务/开源组件）
  - [ ] B. 有限预算（< 1 万/月云服务费）
  - [ ] C. 充足预算（无严格限制）
  - [ ] D. 不确定
```

## 选项设计原则

1. **穷尽且互斥**: 选项之间不重叠，且覆盖绝大多数情况。最后可加"不确定/其他"出口。
2. **场景化**: 不同场景的选项不同。不要对所有用户用同一套通用选项。
3. **量化区间**: 性能、规模类问题给出具体区间而非让用户填数字。
4. **用用户语言**: 避免技术黑话。说"浏览器网页"而非"B/S 架构"。
5. **默认值提示**: 如某个选项是多数同类场景的常见选择，标注"(推荐)"。
6. **3-4 个选项最佳**: 少于 3 个信息量不足，超过 4 个用户决策负担大。
